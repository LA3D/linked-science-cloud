## Current map and proposed enrichment

`updateOrientationForHandle` in the [runtime](../../lib/linked-science-runtime.mjs) skips query results and records identity/version, role/type, optional media type, and ephemeral handle/epoch. It assigns ontology/schema/SHACL references to `parsing-schema`, others to `context-roadmap`. An explicit `orientationContext` shares orientation while inventories remain separate. Source identity and version fields are useful, but do not automatically encode semantic dependencies.

The [PEEK broker scaffold](../../packages/cleanroom-node-repl/src/peek-runtime.mjs) provides five sections, stable IDs, ADD/DELETE/REPLACE and estimated-token eviction. Scores default to 0.5 (runtime references use 0.8/0.7); an optional policy is unconfigured by default. Explicit map retrieval is not automatic prompt presence. Handle invalidation is not semantic freshness validation.

[PEEK sections 3.1–3.2](https://arxiv.org/html/2605.19932v1#S3) distinguish source roadmap from entities/concepts/relationships, separate extraction from local edits, and present a bounded map on each run. The paper learns maintenance from trajectories; this proposed manual comparison is an ablation inspired by that design, not a replication. Its benchmark gains do not transfer as evidence here.

Propose only three or four entries, initially as reviewable text rather than a new runtime schema:

| Entry | Content to review | Evidence and scope |
| --- | --- | --- |
| Source roadmap | Where rendered term documentation and observed RDF fragments live; distinguish documentation from instance observations. | Exact public artifact location, original source URI, observed timestamp/hash; mark missing raw HTML. |
| Context understanding | Protein, annotation, catalytic activity and reaction are distinct nodes in the observed catalytic pattern. | P00533 receipt `observed.graph` elements 2–5 (zero-based); historical instance evidence, not a universal axiom. No accession-specific answer in the reusable entry. |
| Vocabulary meaning | Candidate explanation of annotation/activity/reaction roles, with exact term IRIs. | Review against reacquired primary term definitions before calling it ontology-backed; until then label the explanation as bounded interpretation of observed triples. Do not invent domain/range constraints. |
| Evidence dependency | Each claim lists source URI, content fingerprint or recorded version, evidence locator, observation date, and verification status. | Distinguish an artifact hash from the original RDF-response hash and from a release identifier. On dependency mismatch mark affected claims unverified, then revalidate, replace, or delete. |

Semantic relationships belong in `context-understanding`; reserve `parsing-schema` for serialization structure. A changed source fingerprint should trigger review, not imply the claim is false. A reset invalidates handles even when a historical claim remains supported by its original version. Cross-source claims must list every dependency.

## Smallest practical comparison

Two arms suffice: A, today's generated metadata entries; B, identical metadata plus reviewed semantic entries. Optional C supplies no map while keeping the same source access. Give A and B the same explicit map-read/presentation point at the beginning of every question; record the exact displayed bytes/tokens. This isolates content, and does not claim today's runtime injects a map automatically.

Use one recurring source context and two different follow-up questions after a development warm-up. For the first unscored rehearsal, use the public catalytic material: (a) distinguish which node carries the reaction link; (b) state which claims about reaction detail the retained subgraph can and cannot support. These are proposed development prompts, not new official competency cases. Freeze entries after warm-up. Later, use the reserved manifest questions for independently scored transfer, only after the leakage audit and adequate primary source evidence exist.

Keep separate workspaces/inventories per question and separate orientation contexts per arm. Fresh question prompts must not carry earlier answers/transcripts. Use the same source versions, model/settings, tool instructions, map ceiling (propose 1,024 estimated tokens) and aggregate observation ceiling (propose 8,192 tokens per question, including maps). Record actual token use; do not pad A. Use identical row/cell limits (10/50) and declared cumulative request/byte/attempt budgets across arms; the draft manifest's 12 requests, 8 MB total and 500 result items are starting ceilings for review, not silently active defaults. Do not use display limits to truncate query semantics.

Source acquisition should occur once per matched context when feasible, with identical versioned resident sources made available independently to each arm. No disk persistence feature is required. If reacquisition yields different versions, separate the pair or mark it unmatched. Include acquisition and manual preparation cost in cold-start totals and report warm reuse separately. Start with one paired development sequence; add one reversed-order repetition before treating a difference as stable. This remains a feasibility pilot, not a statistically powered benchmark.

| Measure | Record / interpretation |
| --- | --- |
| Rediscovery | Source reopens, repeated term inspections and orientation-only calls before evidence sufficient for each question; distinguish necessary version checks from avoidable rereads. |
| Correctness | Evidence-supported claims and relationships, correct attribution, complete scope under the question, unsupported claims and calibrated abstentions. Later private scoring compares semantics, not exact query strings. |
| Staleness | One explicitly synthetic dependency-version change after warm-up: does B identify affected entries and revalidate/abstain? Separately reset handles to test residency honesty. Do not present the synthetic change as a new UniProt release. |
| Maintenance cost | Candidate extraction/review time, edits, map tokens, evictions and revalidation calls; include these in total cost rather than counting only saved worker calls. |
| Timing and failure | Transport/call/model time separately; budget exhaustion and source unavailability retained as failures with scope, never as global absence. |

Proceed beyond the pilot only if B reduces rediscovery on different questions without introducing unsupported claims, handles the dependency change honestly, and saves enough repeated work to justify preparation and maintenance. A null or adverse result is a useful outcome; it does not justify automatic policy machinery.
