# Local orientation pilot — 2026-09-08

The pilot observed automatic semantic-map creation, transfer and fresh-worker presentation in both contexts, but **no reduction in full-fixture inspection**. All eight main answers were supported by the supplied local evidence. This is a small development pilot with partial telemetry, not a held-out evaluation or a strict matched-total-token comparison.

## Conditions and evidence

Runtime revision `f9e22bb77b82c4564dee4495a4eab2587dd6663d` / facade 6.4.0 remained unchanged. Actual project MCP identity and cross-call persistence passed without an approval pause. Fresh workers received neutral instructions, a public historical UniProt reconstruction or synthetic catalog, and only their arm's generated map for follow-up. They received no previous answers/chats, evaluator plans or private material. No live scientific requests occurred.

The existing broker maps are task-local. A bounded preflight showed that unchanged entries can be transferred through existing `peek.begin/edit`, then displayed by `orientation.bootstrap`. Both arms used this instrumentation and independently loaded the identical fixture version. Transfer preserved old evidence context/epoch; it did not restore residency. The historical identity row remained separate metadata, never invented RDF.

The [frozen protocol](protocol.json) imposed 12 JS calls, 32,768 observation bytes, a 1,024-estimated-token map and a 4,096-byte bootstrap per question, with 10-row/50-cell views and a five-minute instructed ceiling. All workers inherited the same model/settings with no overrides. Exact total model-token control was unavailable. Missing first-call/input-read telemetry prevents certifying every aggregate observation/time bound. Several workers repaired discovery mistakes; these costs are retained rather than excluded.

## Main observations

Every follow-up re-inspected the entire tiny fixture. B generated four semantic proposals across the main questions, all accepted; each B follow-up evicted its transferred proposal when adding a new one. Different discovery errors explain part of the call-count variation, so fewer calls in one arm are not evidence of a semantic-map speed benefit. There was no justified benefit claim warranting the optional reversed-order repetition.

Manual [semantic review](semantic-review.json) found useful local relationship summaries with no unsupported universal claims when read within their stated source scope. The [citation audit](citation-audit.json) found all 18 retained cited quads in their corresponding fixtures; membership is not semantic truth. The authoring parent reviewed only after capture and never repaired or seeded worker maps. Review time/tokens are unavailable and excluded from worker-cost claims.

Map-transfer JSON was 723 vs 3,932 bytes for UniProt A/B, and 707 vs 2,772 for catalog A/B. These are serialized payload sizes, not complete transport or total model costs. Input rereads, update validation, repairs and evictions add cost. B's semantic summaries did not reduce observed rediscovery here. Whole-call raw telemetry was lost for catalog A warm-up, and several other workers lost their first response through recording errors. Receipts label these gaps; missing values are not zero.

## Version and reset diagnostics

Both catalog workers correctly reported Leena after the same source changed to v2. B bootstrap flagged `dependency-changed`; the worker reobserved native evidence and generated a refreshed entry. Its first ADD reused an existing ID and was rejected; a new ID was accepted and the stale entry evicted. Staleness work took A/B 3/5 JS calls and 3,057/11,063 serialized output-envelope bytes. This includes the adverse repair outcome.

Pre-reset receipts were captured, registered and validated before context resets. Both old-workspace accesses failed with `LS_STALE_WORKSPACE`; both fresh inventories had zero handles/quads. B's retained map showed stale evidence and `source-not-observed`. These are workspace-reset observations, not claims about an additional whole-kernel reset trial. Existing offline tests separately cover kernel reset, atomic rejection, eviction and unavailable-map fallback.

## Delivery and limits

The [aggregate record](results.json) links all 12 worker receipts (eight main questions and four diagnostics); each main/staleness map is separate from its answer receipt. The result registry labels the pilot `trace-derived-partial`. Local artifact references do not restore REPL handles.

`npm test` passed all 171 tests after updating the expected registry counts; the initial failure was the old count assertion. Smoke, project broker verification, result-registry validation, relative-link and whitespace checks passed. No runtime implementation, configuration, dependencies, remotes or public data changed. No push.

The pilot supports feasibility and stale-state honesty, with a null result for inspection savings on these tiny fixtures. It does not establish exact total-cost superiority, held-out competence or broad scientific utility. Any further comparison should first make receipt accounting reliable and expose/enforce total model budgets; do not tune semantic maps on these outcomes.
